# TT_Sniffer 订阅插件化与插件市场调研报告

**调研时间**：2026-10-23
**方法**：逐一核对各项目 GitHub 仓库与官方文档；活跃度用 GitHub API 核实；RSSHub 路由规模按其 `lib/routes` 目录实测统计。
**结论适用范围**：单机、单进程、SQLite、MIT 开源、无专职运维的个人项目。

## 一、结论先行

1. **“订阅”与“插件”必须拆成两层**：订阅是数据（YAML/JSON，可热加载、可 diff、可审核）；插件是代码（需要安装、重启、信任）。把两者合成一个“插件”概念，会让 80% 的简单新增源被迫写代码。
2. **推荐三层扩展**：声明式订阅（默认）→ 进程内 `entry_points` 适配器（官方/可信）→ 进程外 sidecar（不可信/跨语言）。
3. **“市场”做索引，不做托管**：静态 `registry.json` 放 Git，PR 增删；不做一键安装、不做自动更新、不做二进制托管。参照 Homebrew tap 与 FreshRSS 扩展目录，而不是应用商店。
4. **插件 API 要极小**：只承诺 `fetch`/`parse` 与 manifest；去重、打分、存储、告警全部留在核心。核心可以快速迭代，插件不会因打分逻辑变化而崩。
5. **隔离要分级，不要假装 Python 能沙箱**：能力声明只能防误用，防不了恶意代码；不可信插件必须换进程/容器。
6. **“开源 + 无人工运维”与“插件市场”天然冲突**：Miniflux 因此明确拒绝插件系统；RSSHub 靠庞大社区扛住 PR 审核。单人项目应选择“少而稳”的路线。

## 二、背景与现状约束

TT_Sniffer 目前是 FastAPI 单进程 + SQLite 的个人情报聚合器。采集器在 `app/collectors/` 下有 8 个模块；`news.py` 用 `NEWS_SOURCES` 字典暴露 cls/em/sina/ths/wscn，`street.py` 用 `STREET_SOURCES` 暴露 guba/tg，返回统一字典 `{source, ts, title, text, url}`。但 `pipeline.py` 仍按来源类型写了 `news_loop`、`street_loop`、`rss_loop`、`anomaly_loop` 等多条循环，新增一类源要同时改 import、循环和配置三处。

好消息是配置已经外置：`config.example.yaml` 里每个采集器都有 `enabled`/`interval`，RSS 有 `feeds` 列表和 `tier`，股吧有 `codes`/`min_reads`。`requirements.txt` 对 `akshare` 锁定 `>=1.18.94,<1.19`，并注明“接口兼容性风险大”，这正是进程内插件依赖冲突的现实注脚。

需要更正一处背景信息：用户提到的 `github.com/ez4o/Info` 在调研时实测返回 404；GitHub API 显示 `ez4o` 名下仅有 go-try、github-contribution-graph、convert-json-cli、image-resizer 四个仓库，没有 Info。因此本报告不把它当作已核实案例，改用可核实的 **JuFlow**（Python + 插件市场，最接近的样本）与 **InfoHub**（早期项目）作国产对照。引用前验证仓库存在与活跃度，本身也是本课题的教训之一。

## 三、三种插件形态对比

### 3.1 进程内：entry_points 与 pluggy

Python 的 entry points 是“已安装发行版向宿主广告组件”的标准机制：插件在 `pyproject.toml` 声明 group/name/object reference，宿主用 `importlib.metadata.entry_points(group=...)` 发现并 `.load()`（[规范](https://packaging.python.org/en/latest/specifications/entry-points/)、[API](https://docs.python.org/3/library/importlib.metadata.html)）。关键事实是：它只看得见当前环境里已安装的 distribution，新增或升级插件通常要重启；`.load()` 本质是 import，等价于执行任意代码。

pluggy 提供更细的钩子模型：hookspec 定义签名，hookimpl 注册实现，支持 `tryfirst/trylast`、hook wrapper、`register/unregister` 和 `load_setuptools_entrypoints`；pytest 的 1400+ 插件就建立在此之上（[pluggy 文档](https://pluggy.readthedocs.io/en/stable/)）。它适合“核心在固定切面调用插件”，但插件仍在同一解释器、同一 `sys.path`、同一异常栈里。

**优点**：零 IPC 开销、调试体验最好（断点、单步、同进程日志）、可以直接复用现有 `fetch(cfg)` 函数。
**缺点**：隔离性接近零——插件能读 `os.environ`、`config.yaml` 里的 LLM key、代理和 cookie，也能直接打开 SQLite；一个死循环会卡住事件循环，一个 C 扩展 segfault 会带走整个进程；依赖冲突无法解决，同一 venv 里只能有一份 akshare。

热加载尤其要谨慎。`importlib.reload` 会保留模块字典、不重绑外部引用、旧实例继续用旧类定义，而且不是线程安全的（[Python 文档](https://docs.python.org/3/library/importlib.html#importlib.reload)）。因此**代码插件不应热 reload**，只能重启进程或换进程。

### 3.2 进程外：HTTP sidecar 与消息队列

sidecar 用独立 venv/容器/用户运行，通过 HTTP 或 stdio JSON 契约返回条目。优点是依赖各自锁定、崩溃只死 sidecar、可用任意语言、可独立重启实现“热替换”；代价是协议版本、鉴权、超时、重试、日志关联和部署复杂度。

对 TT_Sniffer 有一个硬约束：SQLite 在 WAL 模式下读写可并发，但**写者唯一**，且所有进程必须同机（[SQLite WAL](https://sqlite.org/wal.html)）。所以 sidecar 不应写库，只返回 items，由核心单写。消息队列（Redis/RabbitMQ）对单用户项目过重，v1 不建议引入；若未来多用户，再考虑 Redis Streams。

### 3.3 声明式订阅：RSS/JSON/YAML/CSS selector

声明式订阅把“从哪取、怎么切、字段怎么映射、如何去重、如何打分”写成数据。RSS/Atom/JSON Feed 是外部契约，零代码；HTML 列表页可用 CSS selector 覆盖很大一部分。Miniflux 的 per-feed scraper rules 用 CSS selector，rewrite rules 用小型 DSL（[规则文档](https://miniflux.app/docs/rules.html)）；RSS-Bridge 也提供 CssSelectorBridge/XPathBridge，让用户不写 PHP 就能抓页面（[Bridge API](https://rss-bridge.github.io/rss-bridge/Bridge_API/BridgeAbstract.html)）。

**优点**：无代码执行、天然安全；改 YAML 即可热加载；非程序员可贡献；diff 可读、可审核；测试可用固定 HTML fixture 回放。
**缺点**：登录、签名、分页游标、JS 渲染、WebSocket、二进制解析做不了；selector 漂移时错误信息弱；复杂站点仍然需要代码。

必须澄清一个常见误解：**RSSHub 的 route 是 TypeScript 代码，不是声明式配置**；Huginn 的 scenario 是 agent 图 JSON，但 agent 本身是代码；真正纯声明式的是 Miniflux 的 per-feed rules 和 RSS-Bridge 的 selector bridge。

### 3.4 对比表

| 维度 | 进程内（entry_points/pluggy） | 进程外（HTTP/stdio sidecar） | 声明式（RSS/YAML/selector） |
|---|---|---|---|
| 隔离性 | 低，共享进程与权限 | 高，独立进程/容器 | 不适用（无代码） |
| 依赖冲突 | 高，同一 venv 只能一份 | 无，各自锁定 | 无 |
| 跨语言 | 不可 | 容易（JSON 契约） | 不适用 |
| 热加载 | 难，通常重启 | 易，重启 sidecar 即可 | 易，改文件重载 |
| 调试体验 | 最好（同进程断点） | 中（跨进程日志/追踪） | 差（selector 错误弱） |
| 安全边界 | 无 | 强（容器/独立用户） | 强（数据） |
| 表达力 | 最强 | 强 | 中 |
| 实现成本 | 低 | 中高 | 最低 |
| 适用 | 官方/可信适配器 | 不可信第三方、跨语言 | 长尾简单源、RSS |

### 3.5 判断

按经验分配（非精确统计）：**70% 的新增源应落在声明式**，20% 需要 cookie/签名/复杂分页的落在可信适配器，10% 不可信或跨语言的落在 sidecar。这个比例决定了架构重心：先把声明式订阅做成一等公民，而不是先做插件加载器。

## 四、分发与“市场”机制

### 4.1 三种分发路径

| 模式 | 代表 | 审核强度 | 安装/更新 | 信任来源 | 主要成本 |
|---|---|---|---|---|---|
| 主仓 PR | RSSHub、FreshRSS 官方扩展、RSS-Bridge | 高（人工 review + CI） | 随核心升级 | 维护者背书 | 维护者瓶颈 |
| Git tap/目录 | Homebrew tap、FreshRSS 第三方列表、RSSHub `USER_ROUTES_PATH`、JuFlow Git URL | 无或极轻 | 用户显式添加 | 用户自行判断 | 安全与支持风险 |
| 包 registry | PyPI/npm/RubyGems（Huginn gems、n8n 社区节点） | 平台级扫描/签名，非逐个人工 | 包管理器 | 账号与供应链安全 | 供应链攻击面 |

RSSHub 是“主仓 PR”的极致样本：路由是 TypeScript 模块，按 namespace 目录组织，PR 进主仓；`lib/routes` 下约有 1,959 个命名空间目录、6,177 个 `.ts` 文件（本次 GitHub API 实测）。它没有运行时插件市场；私有路由通过 `USER_ROUTES_PATH` 挂载 `.mjs`，重启生效，文档明确这些模块是 **operator-trusted executable code**，不支持 TypeScript 和 `@/` 别名（[CONTRIBUTING](https://github.com/DIYgod/RSSHub/blob/master/CONTRIBUTING.md)）。这是“官方扩展走 PR、私有扩展走本地目录”的双轨制。

Homebrew tap 是“Git tap”的典型：tap 就是一个第三方 Git 仓库；文档警告 tap 代码会以你的用户权限执行，`brew trust` 可以按单个 formula 授权，而不是信任整个 tap（[Taps](https://docs.brew.sh/Taps)）。它用“完全限定名 + 单项信任”把风险切碎，这个设计值得借鉴。

FreshRSS 把“官方/第三方”分层做得最清楚：官方扩展仓有自动测试与团队审核；第三方扩展只在 README 列链接，并明确“not monitored by the FreshRSS team, so use at your own risk”；安装仍是手工拷贝到 `./extensions`（[Extensions 仓库](https://github.com/FreshRSS/Extensions)、[开发文档](https://freshrss.github.io/FreshRSS/en/developers/03_Backend/05_Extensions.html)）。

JuFlow 是最接近 TT_Sniffer 的样本：Python 项目，提供“插件市场”，但仅管理员可安装，来源是 Git 仓库 URL 或 zip 包，安装后后台采集需重启 worker；README 明确警告“插件在服务器上执行 Python 代码，仅安装你信任的插件”，没有沙箱（[JuFlow](https://github.com/rockbenben/juflow)）。它证明了“Python + Git URL 安装 + 重启生效”可行，也暴露了安全短板。

### 4.2 目录约定与 manifest

建议的订阅仓库结构（草案，不落地）：

```text
tt-sniffer-registry/
  registry.json                 # 唯一索引，PR 修改
  subscriptions/<ns>/<id>.yaml  # 纯声明式，可直接被核心加载
  adapters/<name>/
    pyproject.toml              # entry point: tt_sniffer.adapters
    manifest.yaml               # apiVersion/version/min_core/capabilities
    adapter.py
    tests/fixtures/*.json       # 真实响应样本 + 期望条目数
    README.md
    LICENSE
```

约定要点：`id` 不可变（水位、去重、告警都依赖它）；namespace 不得与内置冲突；每个订阅至少附一个 fixture 和期望输出；CI 做 schema 校验、fixture 回放、manifest 兼容性检查，网络 smoke 测试设为可选，避免 CI 依赖外网。

### 4.3 版本与兼容

- **订阅 schema** 用 `apiVersion: ttsniffer/v1`，与代码插件 API 分开版本化。
- **适配器** 用 `apiVersion: ttsniffer.adapter/v1` + SemVer + `min_core` 范围。SemVer 的规则很明确：不兼容变更升 MAJOR，弃用升 MINOR，纯修复升 PATCH（[semver.org](https://semver.org/)）。
- **能力声明**：`network` 域名白名单、`secrets` 名称、`filesystem` 路径、`max_runtime`。核心启动时校验，不兼容直接禁用并给出可读错误，而不是运行到一半失败。
- **锁定**：registry 记录 git ref、commit sha、wheel sha256；升级必须显式；不自动跟随分支。

### 4.4 审核与安全：审核不是沙箱

微软文档写得很直白：“Extensions have the same permissions as VS Code itself”，Marketplace 会签名并在安装时校验，但校验可以关闭（[VS Code 文档](https://code.visualstudio.com/docs/configure/extensions/extension-marketplace)）。n8n 把未验证社区节点描述为“unverified code from a public source”，并警告它们“have full access to the machine that n8n runs on”；verified 节点才经过安全要求审核（[n8n 风险说明](https://docs.n8n.io/integrations/community-nodes/risks/)）。Homebrew 也警告 tap 代码以用户权限执行。三家的共同点是：**审核和签名降低概率，不提供隔离**。

两个可核实的供应链案例：

- **ctx（PyPI，2022-05）**：维护者邮箱域名过期后被攻击者注册，攻击者走“忘记密码”接管账号，发布恶意版本，读取 `os.environ` 并 base64 外传到 Heroku；影响窗口 5 月 14 日至 24 日，评级 Critical（[GHSA-4g82-3jcr-q52w](https://github.com/advisories/GHSA-4g82-3jcr-q52w)）。教训：包所有权信任可能被一个过期域名击穿。
- **Ultralytics（PyPI，2024-12）**：8.3.41/8.3.42/8.3.45/8.3.46 四个版本被植入挖矿代码；路径是 GitHub Actions 缓存投毒加上未轮换的 PyPI token，恶意代码只存在于 PyPI 制品，GitHub 源码干净，签名 provenance 仍然有效（[Socket 分析](https://socket.dev/blog/ultralytics-pypi-package-compromised-through-github-actions-cache-poisoning)）。教训：来源签名证明“谁构建”，不证明“构建干净”。

对 TT_Sniffer 而言，插件能读 `config.yaml` 里的 LLM key、代理、cookie，也能直接改 SQLite。因此“市场一键安装”本质上是把用户密钥交给陌生人。可行的缓解是 PyPI 已强制 2FA、推广 Trusted Publishing（[PyPI 公告](https://blog.pypi.org/posts/2024-01-01-2fa-enforced/)），但这只保护发行端，不保护宿主。

### 4.5 市场设计结论

**做索引，不做托管；做分级，不做全审；做显式安装，不做自动更新。**

- Tier 0 官方：只收进主仓，随核心测试与发布。
- Tier 1 verified：人工读代码 + 契约测试 + 固定 commit，数量严格限制。
- Tier 2 community：机器校验 + 能力披露 + 免责声明，只列链接。
- Tier 3 private：本地路径/环境变量挂载，类似 RSSHub 的 `USER_ROUTES_PATH`。

`registry.json` 是静态文件，市场 UI 只读它；安装动作由用户显式执行 `tts plugin add <id> --pin <sha>`；不提供自动更新；提供 `SECURITY.md`、takedown 流程和安全公告渠道。

## 五、参考项目对比

| 项目 | 类型/语言 | 扩展机制 | 分发与审核 | 热加载 | 对 TT_Sniffer 的借鉴 |
|---|---|---|---|---|---|
| [RSSHub](https://github.com/DIYgod/RSSHub) | 路由引擎/TS | 路由模块按 namespace 组织，PR 进主仓；私有 `.mjs` 走 `USER_ROUTES_PATH` | 主仓 review；无运行时市场 | 私有路由需重启 | 命名空间 + 单文件路由 + 私有逃生舱 |
| [FreshRSS](https://github.com/FreshRSS/FreshRSS) | RSS 阅读器/PHP | `metadata.json` + `extension.php`，`registerHook` 挂 `EntryBeforeInsert`、`FeedBeforeActualize` 等 | 官方仓测试/审核；第三方仅列链接 | 启用/禁用即生效 | 官方/第三方分层 + 钩子切面 |
| [Miniflux](https://github.com/miniflux/v2) | RSS 阅读器/Go | **无插件系统**；per-feed CSS scraper rules 与 rewrite rules | 核心内置 | 规则随 feed 保存 | 用声明式规则覆盖长尾；克制 |
| [Folo](https://github.com/RSSNext/Folo) | AI RSS 阅读器/TS | 复用 RSSHub 路由；MCP 服务接入；公开资料未见第三方代码插件市场 | 应用内集成 | 不适用 | 不自建源覆盖，复用生态 |
| [Huginn](https://github.com/huginn/huginn) | 自动化/Ruby | Agent 可写成外部 gem，经 `ADDITIONAL_GEMS` 注入 | RubyGems | 需重启 | gem 化打包 + 显式注入 |
| [RSS-Bridge](https://github.com/RSS-Bridge/rss-bridge) | Feed 生成/PHP | Bridge 类继承 `BridgeAbstract`，实现 `collectData()`；管理员用 `enabled_bridges` 白名单 | 文件放入 + 重启；无市场 | 需重启 | 管理端白名单 + 统一 Bridge API |
| [JuFlow](https://github.com/rockbenben/juflow) | 聚合阅读器/Python | 插件市场，管理员从 Git URL/zip 安装；无沙箱；worker 重启 | 管理员显式安装 | 部分生效，采集需重启 | 最接近的 Python 样本；其风险提示即反面教材 |
| [InfoHub](https://github.com/Jinkin-92/Infohub) | 本地聚合/TS | 未见插件/订阅格式文档，仓库仅 1 次提交 | 不适用 | 不适用 | 早期项目不宜作为架构依据 |

Miniflux 的 FAQ 值得全文引用：为什么没有插件系统？“Because this software has a minimalist approach. Because implementing a plugin system increases the complexity of the software. Because people do not maintain their plugins after a while.”（[FAQ](https://miniflux.app/faq.html)）这三条几乎预言了单人开源项目做插件市场的结局：**插件会腐烂，维护成本会回到核心**。

从这些项目可以提炼六条可借鉴模式：命名空间与单文件路由（RSSHub）；官方/第三方信任分层（FreshRSS）；声明式规则覆盖长尾（Miniflux/RSS-Bridge）；不自建源覆盖、复用 RSSHub（Folo）；包化加显式注入（Huginn）；插件安装必须显式且展示风险（JuFlow）。

## 六、TT_Sniffer 推荐架构草案

### 6.1 分层

```text
[subscriptions/*.yaml]  (热加载)
          |
      Scheduler  ---> 声明式 Parser (RSS/JSON/HTML)
          |       ---> Adapter (entry_points, 可信, 启动加载)
          |       ---> Sidecar (stdio/HTTP, 不可信, 独立重启)
          v
   Normalize -> Dedupe -> Impact/Score -> SQLite(单写者) -> SSE/Webhook
```

核心原则：**适配器只负责“取回并解析成 RawItem”，核心负责之后的一切**。这样插件 API 可以长期稳定，而去重、打分、告警可以快速迭代。

### 6.2 统一订阅描述（YAML 草案）

```yaml
apiVersion: ttsniffer/v1
kind: Subscription
metadata:
  id: guba-600519          # 不可变；水位/去重/告警都依赖
  name: 东财股吧-贵州茅台
  maintainers: ["@you"]
spec:
  source:
    kind: http             # rss | http | akshare | adapter | sidecar
    url: https://guba.eastmoney.com/list,600519.html
    adapter: guba          # kind=adapter 时必填
  schedule: {every: 5m, jitter: 0.2, timezone: Asia/Shanghai}
  fetch:
    method: GET
    headers: {User-Agent: "TT_Sniffer/0.4"}
    timeout: 20s
    proxy: none
    conditional: {etag: true, last_modified: true}
  parse:
    kind: html
    list: "div.articleh"
    fields:
      title: {sel: "a.title", attr: text}
      url:   {sel: "a.title", attr: href, absolute: true}
      ts:    {sel: "span.l3", attr: text, format: "%Y-%m-%d %H:%M"}
      text:  {sel: "a.title", attr: text}
  normalize:
    canonical_url: true
    strip_query: ["utm_*"]
    max_age_days: 3        # 首轮回灌上限，防旧文刷屏
  dedupe: {keys: [canonical_url, content_hash], simhash_distance: 3}
  impact:
    base: 30
    rules:                 # 规则 DSL 草案，由核心解释
      - {match: "title ~ /减持|立案|问询/", add: 35}
      - {match: "entity in watchlist", add: 20}
    decay_hours: 48
  limits: {per_host_rps: 0.2, burst: 1, max_items: 200}
  routing: {tier: street, tags: [cn, equity, social], enabled: true}
```

### 6.3 适配器契约与加载

```python
# 契约草案（不落地到 app/）
class AdapterManifest(BaseModel):
    api_version: str          # "tts.adapter/v1"
    name: str
    version: str              # semver
    min_core: str
    capabilities: Capabilities  # network/secrets/filesystem/max_runtime

class Adapter(Protocol):
    manifest: AdapterManifest
    async def fetch(self, sub: Subscription, ctx: Context) -> list[RawItem]: ...
    def parse(self, raw: RawItem, sub: Subscription) -> list[Item]: ...

def load_adapters() -> dict[str, Adapter]:
    found = {}
    for ep in entry_points(group="tt_sniffer.adapters"):
        mod = ep.load()                       # 执行插件代码，必须信任
        m = mod.manifest
        if not api_ok(m.api_version, CORE_API):
            log.warning("skip %s: incompatible api", ep.name)
            continue
        found[m.name] = mod
    return found
```

  filesystem: []

async def run_one(sub, adapter):
    host = urlparse(sub.source.url).hostname
    async with limiter(sub.limits, host=host):
        raws = await asyncio.wait_for(adapter.fetch(sub, ctx), sub.fetch.timeout)
    items = [normalize(x) for r in raws for x in adapter.parse(r, sub)]
    items = [x for x in items if await dedupe.is_new(x)]
    for x in items:
        x.tier = sub.routing.tier
        x.score, x.impacts = impact.score(x, sub.impact, watchlist)
    await store.insert_many(items)   # 唯一写者，幂等插入
    bus.publish(items)

### 6.5 限流、去重、打分

**限流**：按可注册域名做令牌桶，而不是按 URL；全局并发信号量；抖动；指数退避并尊重 `Retry-After`；支持 ETag/If-Modified-Since；连续失败触发断路器；首轮用 `max_age_days` 截断。反爬不是压测许可，订阅级限流应内建，避免开源用户照抄配置后被封 IP。

**去重**：规范化 URL（去 utm、统一 host、解析跳转）+ 内容哈希 + simhash 近重复。现有 `norm_id(source,title,text)` 与 `app/simhash.py` 可直接复用。跨源重复应“分组”而不是“丢弃”，以便影响打分聚合。

**打分**：核心独占。订阅只能提供 base、关键词/实体规则、tier 乘数和时间衰减；适配器可返回实体提示，但不能直接写最终 score。分数变更要记录 reason code，便于审计和 UI 解释。

### 6.6 热加载矩阵

| 对象 | 能否热更 | 方式 |
|---|---|---|
| 订阅 YAML | 是 | watch + 校验通过后原子替换 |
| 关注列表/打分词表 | 是 | 现有 KV/UI 已支持 |
| 适配器代码 | 否 | 重启；提供 safe mode |
| sidecar | 是 | 独立重启 + 版本握手 |
| schema/apiVersion | 否 | 迁移 + 重启 |

### 6.7 与现有代码的映射

| 现有 | 目标 |
|---|---|
| `config.collect.*` | `subscriptions/*.yaml` |
| `NEWS_SOURCES`/`STREET_SOURCES` | 内置适配器注册表（保持 dict 返回） |
| `pipeline.news_loop/street_loop/...` | 统一 Scheduler |
| `Item` | 不变，作为核心数据模型 |
| `norm_id`/`simhash` | Dedupe 服务 |
| `scoring.py`/`impact.py` | 核心打分，不进插件 API |

迁移顺序建议：先把现有 fetch 函数包装成 builtin adapter，保持字典返回；再由 `config.collect` 生成等价 YAML；最后删除专用循环。每一步都可回滚，避免大爆炸式重构。

## 七、与“开源 + 无人工运维”的冲突与折中

| 冲突 | 表现 | 折中 |
|---|---|---|
| 市场审核 vs 无收入 | 人工读代码、处理举报、应急下架，都是持续人力 | 静态索引 + 机器校验；verified 严格限量；community 只列链接并免责 |
| API 稳定 vs 快速迭代 | 每加一个 hook 就多一个兼容承诺，社区插件会拖住核心 | 只承诺 `fetch`/`parse` + manifest；去重/打分/存储不进 API；弃用期两个 minor |
| 安全 vs 易用 | 一键安装最易用，也最容易把密钥交给恶意插件 | 只允许本地路径/显式 Git URL 安装；安装时展示 capabilities；默认关闭自动更新；提供 safe mode |
| 长尾覆盖 vs 维护 | 插件作者流失后，issue 回到核心 | 核心只维护高价值源；插件标 `last_verified`；90 天无维护标 stale，不删除；CI 定期跑 fixture |
| 单进程 SQLite vs 隔离 | sidecar 写库会破坏单写者假设 | sidecar 只返回数据，核心单写；WAL + busy_timeout；禁止长事务 |
| 开源协作 vs 支持负担 | 用户带着第三方插件的问题来提 issue | 诊断页输出插件版本/错误；issue 模板强制附日志；明确不承诺第三方支持 |
| 许可与数据版权 | 插件可能内置绕过付费墙/登录的逻辑 | 核心 MIT，SDK MIT；插件各自许可；保留现有数据版权免责声明；不收录绕付费墙插件 |

最根本的冲突是**“市场”意味着承诺**。RSSHub 能承受，是因为有足够大的社区和贡献者基数；FreshRSS 能承受，是因为把官方与第三方切开；Miniflux 选择不承诺。TT_Sniffer 是单人项目，理性的选择是：**先做“订阅格式 + 官方适配器”，再做“只读索引”，最后才考虑 sidecar 生态**。

## 八、结论与路线图

推荐形态可以概括为一句话：**声明式订阅是一等公民，entry_points 适配器是二等公民，sidecar 是三等公民；“市场”是 Git 索引，不是应用商店。**

- **阶段一**：冻结订阅 schema；统一 Scheduler；把现有采集器包装成 builtin adapter；支持 YAML 订阅；加诊断页与 `--no-plugins` safe mode。
- **阶段二**：发布适配器 API 与契约测试工具；建立静态 `registry.json`；安装时展示 capabilities；文档先教“写订阅”，再教“写适配器”。
- **阶段三**：只有出现真实外部需求时，才加 stdio/HTTP sidecar、容器隔离和签名索引；不急于做“插件市场”UI。

验收标准很具体：新增一个 RSS 源只改 YAML；新增一个需要 cookie 的源只加一个 adapter 文件；禁用所有第三方插件后核心功能不受影响；任何插件崩溃都不会带走采集主循环。

这套方案的关键不是技术复杂度，而是克制：把插件 API 做小，把信任分级，把自动更新关掉。对开源个人项目而言，这比“像 VS Code 一样的热闹市场”更可持续。
