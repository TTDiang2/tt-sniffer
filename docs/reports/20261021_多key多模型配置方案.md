> 状态：**已实现并过智者门（2026-10-21 晚）**，提交含 16+1 项新测、全量 pytest 285 passed。

## 一、目标回顾

1. 「翻译」「一句话戏谑评论（精筛 one_line）」「AI 对话分析」拆成**三条独立通道**，各自可配 `base_url`（platform）/ `model` / key 池（3–5 个）/ `system_prompt`。
2. 轻量模型走翻译（省成本、快），更强模型走对话分析。
3. key 池轮换 + 降级；**旧单 key 配置完全兼容**（不写 channels 时行为与现在逐字节一致）。

## 二、配置结构（建议）

`config.yaml`（示例同步进 `config.example.yaml`）：

```yaml
llm:
  enabled: true
  # ---- 旧字段保留为全局兜底：channels 缺失或通道字段缺失时继承这里 ----
  base_url: https://api.agnes-ai.cn/v1
  model: agnes-3.0-flash
  api_key_env: TTSNIFFER_LLM_API_KEY      # 旧单 key：自动并入各通道 key 池
  min_score: 55          # 精筛触发线（comment 通道沿用）
  round_cap: 20

  # ---- 三通道（全部可选；不写 = 全部继承上面的旧字段，零行为变化）----
  # keys_env 合并语义（钉死）：通道写了 keys_env = 完全取代（不与旧 api_key_env
  # 自动合并、不去重）；通道没写 keys_env = 继承旧 api_key_env 单 key 池。
  channels:
    translate:                            # 外网条目标题+摘要翻译
      base_url: https://api.agnes-ai.cn/v1
      model: agnes-3.0-flash              # 轻量模型
      keys_env:                           # key 池=环境变量名列表（密钥不进 config 文件）
        - TTSNIFFER_LLM_API_KEY           # 写了本列表即完全取代旧 api_key_env（不自动合并）
        - TTSNIFFER_LLM_API_KEY_2
        - TTSNIFFER_LLM_API_KEY_3
      temperature: 0.1
      max_tokens: 500
    comment:                              # LLM 精筛 + 一句话戏谑评论
      base_url: https://api.agnes-ai.cn/v1
      model: agnes-3.0-flash
      keys_env: [TTSNIFFER_LLM_API_KEY, TTSNIFFER_LLM_API_KEY_2]
      system_prompt: ""                   # 空=用内置 PROMPT；可改成更/更不戏谑的版本
      temperature: 0.1
    chat:                                 # AI 对话分析（抽屉）
      base_url: https://api.agnes-ai.cn/v1
      model: agnes-4-plus                 # 更强模型（示例，按用户账户实际可选改）
      keys_env: [TTSNIFFER_LLM_API_KEY]
      system_prompt: ""                   # 空=用内置 ANALYST_SYSTEM_TEMPLATE
      temperature: 0.3
```

要点：

- **密钥永不落 config 文件**（沿用现行 `api_key_env` 惯例）：`keys_env` 是环境变量**名**的列表，密钥本体在用户环境/run.bat 里设。避免密钥随 config.yaml 备份/截图泄露。
- **keys_env 合并语义（防重复/歧义，钉死）**：通道显式写 `keys_env` = 完全取代旧 `api_key_env`（哪怕列表里恰好包含旧名，也不做二次合并）；通道未写 = 继承旧 `api_key_env` 成单 key 池。
- `system_prompt` 语义分通道：**comment 通道只覆盖内置 PROMPT 中 one_line 的风格描述句**（拼接进内置模板，保住「只输出 JSON」的输出契约——全模板替换会炸掉 enrich 的 JSON 解析，禁用）；**chat 通道为完整 system 替换**（自由文本输出，无 JSON 契约）；translate 保持内置模板（字段保留对称性，非空时同 comment 规则只覆盖风格段）。
- `enabled`、`min_score`、`round_cap`、`translate` 并发信号量等仍是全局项，不按通道拆。

## 三、key 池轮换与降级策略（建议）

实现为 `llm.py` 内一个小类 `KeyPool`（无新依赖）：

1. **轮换**：round-robin。每次请求取下一个 key；进程内存放游标，不持久化。
2. **降级**：请求失败且 `_retryable`（429/5xx/网络类，沿用现判定）→ **立即换下一个 key** 重试，同一 key 进入 60 秒冷却；全池冷却中 → 取冷却最早结束的 key 并退避等待（上限仍受每条目总尝试次数=3 约束）。
3. **不重试的失败**（401/400）：直接失败并 log 出 key 的 env 名（不打印密钥），提示用户该 key 配错。
4. 401 特例：某 key 连续 2 次 401 → 该 key 标记禁用到重启（防坏 key 烧掉每条目 1 次尝试预算）。
5. 每条目总 HTTP 尝试次数**维持各通道现状**：translate 3 次（retries=2）、comment 1 次（retries=0）、chat 单次流式。**key 轮换只发生在各通道现有尝试槽位内**——comment 单次尝试即单 key，失败不因 key 池而加试（保证「不写 channels 时逐字节一致」）。key 池只改变「用哪把钥匙试」，不放大请求量。（规模建议见 §七）

## 五、迁移与兼容

- **零配置迁移**：不写 `channels` → 加载器把旧 `base_url`/`model`/`api_key_env` 展开成三通道同款单 key 池，行为与现状一致（回归由现有 268 个测试保证）。
- **加 key 逐步走**：先给 translate 加 `TTSNIFFER_LLM_API_KEY_2/3` 环境变量与 `keys_env`，观察统计脚本 429 归零，再扩 comment/chat。
- **换更强 chat 模型**：只改 `channels.chat.model` 一行，与翻译通道互不影响。
- 统计脚本（`20261021_翻译与评论成功率统计.md`）口径不变，key 池上线后重跑即可对比。

## 七、影响面脚注

- 双进程（8787/8788）共写同一 `data/sniffer.db` 与日志：KeyPool 状态按进程独立，规模建议（§三）以「8788 禁 LLM 或独立 key」为前提，否则实际吸收力按 key 数减半估。
